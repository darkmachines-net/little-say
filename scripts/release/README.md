# Release implementation

Artifact publication uses `.github/workflows/cut-release.yml`. `npm run release:cut -- <stage>` invokes `unified.ts`; `release:plan` runs the read-only plan/check/export path. The workflow exposes only `bump` and `profile`; new plans always use automatic selection. Use the workflow for mutations. `recover-release.yml` can audit a terminal internal cut and publish only its missing completion receipt after all original operations are verified. Standalone source checks use **Check** or `release:validate`. Provider commands use pinned dependencies and publication uses the exact protected source tree.

| File | Responsibility |
| --- | --- |
| `contract.ts` | Versioned plan, portable native baseline, operation journal, and completion receipt contracts |
| `inputs.ts`, `planner.ts` | Committed component/dependency identities, per-profile comparisons, automatic selection and the requested server/native version increment |
| `provenance.ts` | Shared-engine decision digest, selected stage graph, and separate source/workflow/toolkit revisions |
| `metadata.ts`, `candidate.ts` | Combined version-only PR, normal protection/review, full repository/PostgreSQL checks, and exact merged-tree validation |
| `journal.ts`, `operation.ts` | Immutable draft-release assets, per-operation sequence/IDs, recovery reconciliation and ambiguity stops |
| `retirement.ts`, `reconciliation.ts` | Automatic retirement of unpublished stale candidates; separate preview/apply audit for terminal internal image/build cuts, preserving partial publications without claiming completion |
| `image.ts` | Legacy image verification, multi-architecture immutable publication, and guarded `latest` promotion |
| `expo.ts`, `eas-credentials.ts`, `ios-signing.ts`, `environment.ts` | Pinned EAS reads, remote identities/credentials/environment, selected iOS profile entitlement checks, runtime resolution and export |
| `cloud.ts` | Finished platform builds, artifact SHA-256 proof, and exact-ID production submissions |
| `ota-artifact.ts` | Durable exact export archives and shared-engine manifest verification before provider intent |
| `ota.ts` | Runtime eligibility/retirement/deduplication, validated exports, raw group/payload verification |
| `summary.ts` | Selected/skipped component decisions, versions, runtime exclusions, and verified artifact links |
| `completion.ts`, `completion-recovery.ts` | Verified completion receipt and full journal archive; restricted recovery of fully published and deployed internal cuts |

`apps/mobile/fingerprint.config.js` is shared by EAS and the local fingerprint subprocess. It includes native modules/plugins, resolved Expo configuration, native identity, selected build profile/toolchain, and its own policy. Version-only overlays flow through `release-metadata.cjs`. Raw metadata is replaced with resolved content so an older runtime can be checked without editing tracked source. The hook excludes only other-platform/web configuration and non-native scripts; full fingerprints retain the selected runtime and native settings. Kotlin `.kotlin` compiler sessions are excluded inside discovered dependency/plugin roots, alongside the SDK's generated Gradle/build/CXX exclusions; actual native/plugin source remains hashed. The selected platform is passed explicitly by wrappers. `.gitattributes` keeps tracked text bytes portable across operating systems.

The fingerprint policy explicitly uses the `strict` preset. SDK 58 defaults to `balanced`, which omits version fields and hashes native dependencies by package identity; our release gate retains full native source/configuration sensitivity.

Planning normalizes the three allocated version fields; publication never treats that normalized identity as full runtime proof. Each OTA baseline also requires full fingerprint equality after resolving its own native version metadata, same project/server/profile/environment, and source ancestry. The committed `release-policy.json` lists imported verified cloud baselines and retired runtimes. Retirement is explicit and does not delete prior evidence.

Cut and recovery expose GitHub/Expo tokens only to release command steps. Fingerprint, runtime-resolution, bundle-export, and validation children receive the `sourceEnvironment` allowlist: portable process/toolchain settings, declared channel/version/platform and Google iOS scheme inputs, the two supported public API URL variables, and test database/emulator settings. Other inherited or remote names must be explicitly added to that contract before source can use them. Authenticated EAS transport still needs its token and can evaluate Expo configuration; source children also share the runner and home directory. These environment boundaries reduce credential exposure but do not provide isolated publisher runners.

Candidate assets are append-only and operation keys have one writer each. `intent` records precede remote requests; `running` records persist accepted IDs; `complete` records contain verified evidence. Draft journal reads require repository push/Contents write permission even when the action only inspects state. A failed request response is not evidence that no operation occurred. Recovery queries exact run markers or build-associated submissions; zero matches after an unresolved intent, or multiple matches, stop for operator reconciliation. Store submission retries for every saved plan schema require a fresh provider `canRetry` observation and verified original build, source, artifact hash, and destination. They use `submit:retry` on the exact failed ID, retaining all prior IDs and retry proof; a generic terminal failure cannot authorize another upload. Unknown, expired, canceled, or wrong-destination submissions remain blocking. Historical schema-1 records retain their saved runtime, selection, and stage requirements; they do not bypass current retry safety checks. Normal retries cannot change the run's input plan or allocated versions. Persisted `mode` still accepts historical `force_all` records; the planner has no mode input. Saved native patch allocations remain unchanged even when their original bump was minor/major. The separate `plan` command is the only preview entry point; the removed mode environment switch cannot force new work, and a legacy `RELEASE_DRY_RUN=true` fails before side effects with instructions to use `release:plan`.

Completion is deliberately last. A published receipt, not a server Git tag, workflow start, queued build, or candidate draft, advances client baselines. The `promote-server` stage advances the verified image's `latest` alias before the reusable workflow calls the shared darkmachines deployment API. Selected server deployment must return a completed healthy result before OTA and required release completion. New OTA-only/native-only work skips deployment; historical plans preserve their original gate. Production `submit` verifies accepted exact-build submission IDs, `submit-complete` waits independently, and completion requires finished submissions. The alias and server may already change when a later provider operation fails; retries retain the existing journal. Provider operations and aliases cannot be one atomic transaction. See [the operator recovery guide](../../docs/releases.md#workflow-and-recovery) and [webhook configuration](../../deploy/self-hosted/README.md).

Tests use in-memory provider/journal failure injection and temporary Git repositories, plus the real Expo fingerprint library. Keep acceptance tests focused on source movement, version allocation, provider identity, and recovery rather than reproducing implementation details. Run `npm run check`, `npm run test:services`, and `actionlint` before changing the workflow contract. Actual EAS signing/build/submission/OTA onboarding is a separate publishing validation stage.

New plan schema 2 and native baseline schema 3 distinguish fingerprint runtimes from historical appVersion records. The transition requires new native baselines; legacy records are preserved without asserting cross-policy compatibility. Every newly built runtime receives its current OTA bundle even when JavaScript inputs are unchanged. `provenance.ts` seals all plan decisions and selected stage prerequisites with separate application source, workflow, and toolkit revisions. Modern OTA exports are archived before operation intent, restored into fresh verified storage, and retained at completion before deleting the candidate. Shared-engine changes must be synchronized from the template and verified byte-for-byte, never edited in the vendored directory.
