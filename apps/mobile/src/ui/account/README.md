# Account entry and management

`AccountScreen` supplies the native safe-area modal, a headerless `AccountWelcome`, and shared headers for authentication forms handled by `AccountEntry`. Signed-in controls live in [Settings](../README.md#settings): `AccountOverview.tsx` supplies the Account group and backup recovery details, `AccountSettingsPage` supplies the shared Settings page chrome, and `AccountManagement` handles one account action per page. The [account service](../../services/README.md#accounts-and-sync) owns authentication, backup scheduling, state derivation, and data retention; UI never infers backup health from message text.

The headerless Open canvas welcome centers the bundled mountain, decorative word cards, and **Little Say: Learn to Talk!** heading on warm cream. Entry places branded **Sign in with Google** above **Create Little Say account** and **Sign in with Email** at the bottom. The provider button uses [bundled provider branding](../../../assets/auth/README.md), registration is filled green, and email sign-in is outlined white. Artwork sizing reserves room for the configured action count; the entire screen scrolls when small windows or larger text need more room. Decorative art is static and hidden from assistive technology, while the heading receives screen focus. Forms retain their shared route headers and credential lifecycle. The public [web landing page](../../website/LandingPage.web.tsx) reuses the exported `WelcomeArtwork` and `welcomeBackground`.

Sign-in is required before setup or saved boards on web, iOS, and Android. Provider entry appears only on welcome and uses the login exchange for new and returning users: Firebase creates the identity on its first successful provider sign-in. Android, iOS, and browser welcome expose the same three actions when Google is configured. Google uses its native dialog on mobile and a Firebase popup on web. Apple is excluded even when older configuration lists it. Email registration, sign-in, and reset forms do not repeat provider buttons; disabled server providers are hidden, and readiness, busy state, and Expo Go support gate actions. Successful authentication returns Home after any [initial starter installation](../../services/README.md#accounts-and-sync) is saved. New accounts can play or edit their examples immediately. Empty devices without an initial snapshot defer setup and board creation until cloud restoration succeeds. Home centers a large spinner and **Syncing your content…** heading in the available page below its header, replacing board headings and creation controls; failure offers **Retry sync** in that same area. Restored boards appear automatically, or setup opens when the cloud library is empty. Cached libraries remain usable during background sync and offline. Home's **Refresh content** navbar button starts a manual sync and replaces its icon with an indeterminate spinner while syncing or saving locally; its fixed footprint keeps the header and board list stationary. It stays disabled while busy or when sign-in, verification, or deletion blocks backup. Explicitly opened Settings pages stay open and remain navigable during restoration.

The Settings overview omits routine backup status and timestamps. The Account group shows **Verify email** only while verification is needed and **Backup needs attention** only after a failed backup. Deletion remains available in the same group. Backup details remain available for error recovery and existing direct links, showing the last acknowledged sync, included/local-only data, server errors, and conflict-copy information. There is no backup toggle, browser-storage permission section, or redundant Continue button; Settings retains its caller so Back returns to boards, the editor, or setup.

Authentication forms live under `/app/account`; signed-in actions live under `/app/settings`:

| Route | Screen |
| --- | --- |
| `/app/account` | Legacy Settings overview link; required welcome when signed out |
| `/app/account/{login,register,reset}` | Authentication forms |
| `/app/settings/backup` | Backup error recovery and retained direct links |
| `/app/settings/account/sign-in-methods` | Linked and available methods |
| `/app/settings/account/{link-email,link-google}` | Fresh identity confirmation and provider linking |
| `/app/settings/account/verify-email` | Check verification or resend email |
| `/app/settings/account/sign-out` | Confirm sign-out and retention of downloaded boards |
| `/app/settings/account/delete` | Explain deletion and require fresh identity proof |

Web routes support direct links, refresh, and Back/Forward. Legacy management links resolve to the Settings destinations; retired `link-apple` links resolve to sign-in methods; legacy authentication links still resolve to `/app/account` forms. Native navigation retains an in-memory page stack that resets after authentication; direct links fall back to logical parents, with linking returning to sign-in methods. Signed-out management links show required entry. Page remounts discard credentials; credentials never enter history or persisted UI state. Account actions guard Settings Back and browser history; background sync allows navigation while blocking overlapping account mutations.

Provider linking requires a currently linked Google/email method. Legacy Apple-linked accounts retain their sessions but must use a previous compatible client for Apple-dependent actions, including deletion and its required revocation. The current client never offers Apple linking or bypasses revocation. Pending deletion blocks verification and linking, leaving sign-out available. Expo Go explains unavailable Google actions at the action that needs them.
