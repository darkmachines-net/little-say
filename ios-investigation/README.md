## Three investigation approaches

1. **Listener lifetime and terminal delivery.** Installed expo-audio 57.0.5 AudioPlayer.swift registers the notification before playImmediately (102-109), holds the observer (49), and emits didJustFinish only on its end-notification branch (442-470). App audioPlayback registers its JS listener before asynchronous play and retains the subscription/player in cleanup. The native registry retains the player. No source evidence found of premature disposal. The real adapter/hybrid/queue model completed 100 repeats, including terminal true followed by false snapshots, with exactly one disposal each. This does not exercise native notification delivery or garbage collection.
2. **End status and generated WAV duration.** Native currentStatus defaults didJustFinish to false (146); the true value is a one-shot event, not a durable snapshot. Withholding that event deliberately left the loaded modeled card active until the existing 20-second queue watchdog, then advanced pending playback. This is fault injection, not reproduction or evidence iPad dropped an event. Actual pcmToWav generated consistent RIFF/data lengths and 24-kHz mono 16-bit duration for 2, 24000, 48000 and 960000 PCM bytes; rejected empty, odd and oversized PCM. No AVFoundation decode or affected clip inspected. Silence can precede file duration; audible end alone does not establish file end.
3. **Cancellation and session handoff.** Modeled pause at 0.2/0.5 seconds preserved current-word sequencing; stop discarded pending work; stale completion/error could not settle a new session. Native AudioModule.swift completion schedules session deactivation after 100ms and skips it if any playable isPlaying (828-841). Interaction with a buffering successor is a hypothesis requiring native trace, not a demonstrated race. Changing session policy or treating every paused status as completion would be speculative and could truncate valid speech. Existing deferred-mode-cancel and latest-pending maintained tests supplement this model.

Four isolated investigation tests passed. They execute actual application adapter/hybrid/queue and PCM wrapper, with mocked Expo events and fake JS timers. ## Evidence limits and next discriminator

ZBook is Windows. Available-target inspection found no attached adb device, Apple device/service or Apple runtime tooling. No device software installed. Four passing models cannot establish an iPad root cause, and desktop Chrome evidence cannot substitute for native Before/After evidence.

The precise missing discriminator is a generated-clip run on the reported iPad with matched app/native versions and playback identity: record loaded/currentTime/duration/playing/isBuffering/didJustFinish/error status through audible end; tap/enqueue, completion and cleanup/queue-settlement events; any interruption; and whether state survives beyond the existing 20-second watchdog. A delivered didJustFinish with no settlement points toward JS cleanup/state; absent didJustFinish with end position points toward native event delivery; a paused/buffering successor points toward interruption/session handoff. These are proposed trace interpretations, not findings. Required unknowns: iPadOS and Expo Go versions, served app revision, affected clip and its duration, frequency and stuck duration.

No further product patch or arbitrary timeout change is justified by these checks.
